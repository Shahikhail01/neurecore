# Accounting Sidecar

> `infra/accounting-sidecar/` — Python FastAPI service for Beancount ledger + numpy-financial compute. Last refreshed: 2026-07-31.

Plan ref: **NC-ACCT-IMP-1** (Accounting Capability Implementation, Phase 1).

---

## 1. Why a sidecar?

- **Compute (TIER-1, stateless):** NPV, IRR, MIRR, amortisation,
  depreciation. Done with `numpy-financial`.
- **Ledger validation + report generation (TIER-1, stateless in MVP):**
  Beancount parses the submitted ledger text and produces reports.
- **Production reports (stateful-but-isolated):** reads an mmap'd Beancount
  snapshot regenerated by NestJS as part of every write transaction.
- **Why Python:** ecosystem (`beancount`, `pandas`, `numpy-financial`) is
  Python-only; rebuilding it in TS would be costly and fragile.
- **Why a separate process:** strict isolation from Postgres — the
  sidecar has no `DATABASE_URL`. Every data access is mediated by the
  NestJS gateway.

## 4. Endpoints

### 4.1 Unauthenticated
- `GET /healthz` → `{status, service, version}`
- `GET /readyz` → `{status: ready}`

### 4.2 `/v1/*` — HMAC-scoped bearer required
All routes under `/v1/` go through `APIRouter(prefix="/v1",
dependencies=[Depends(require_accounting_token)])`. So if you forget the
bearer, you get a 401 from FastAPI's dependency injection.

| Endpoint | Body | Returns |
|---|---|---|
| `POST /v1/compute/investment/npv` | `{rate, cashflows[]}` | `{computationId, npv, converged}` |
| `POST /v1/compute/investment/irr` | `{cashflows[]}` | `{computationId, irr, converged}` |
| `POST /v1/compute/investment/mirr` | `{cashflows[], financeRate, reinvestRate}` | `{computationId, mirr, converged}` |
| `POST /v1/compute/loan/amortize` | `{principal, rate, term}` | `{computationId, schedule[]}` |
| `POST /v1/ledger/validate` | `{beancount: "..."}` | `{valid, errors[]}` |
| `POST /v1/reports/income_statement` | `{periodId, ...}` | report |
| `POST /v1/reports/balance_sheet` | `{asOf, ...}` | report |
| `POST /v1/reports/cash_flow` | `{periodId, ...}` | report |
| `POST /v1/reports/trial_balance` | `{asOf, ...}` | report |
| `POST /v1/reports/equity_statement` | `{periodId, ...}` | report |
| `GET  /v1/snapshot/{tenantId}/{periodId}` | — | binary snapshot (mmap region) |

### 4.3 Computation IDs
Each compute response includes a `computationId` =
`sha256(rate + cashflows + ts)[:16]`. Used for idempotency + audit trail
on the NestJS side.

## 5. Beancount snapshot

### 5.1 What it is
- One binary file per `(tenantId, periodId)`, generated server-side by
  NestJS from `JournalEntry` rows.
- The sidecar `mmap`s it (read-only) for low-latency report generation.
- Refreshed as part of the outbox handler after every commit (Phase 1k).

### 5.2 Snapshot store (`snapshot.py`)
- Provides `get_store().open(tenantId, periodId)` → read-only handle.
- Locking: per-tenant writer lock held by NestJS during regen; readers
  (the sidecar) never block.
- Recovery: if the snapshot is missing, the sidecar returns `503` with
  `{reason: "snapshot_not_ready"}` and NestJS regenerates synchronously.

### 5.3 Why not just call Postgres from the sidecar?
Because Beancount reports are best computed from a flat text ledger, and
the snapshot is the canonical flat representation. It also gives us a
cheap point-in-time snapshot for audit + reproducibility.

## 6. NestJS gateway — `backend/src/modules/accounting/`

### 6.1 Module
`backend/src/modules/accounting/accounting.module.ts` wires:
- `AccountingController` — REST surface.
- `AccountingService` — orchestration.
- `AccountingTokenService` — issues scoped HMAC tokens for the sidecar.
- `LedgerRepositoryService` — the only writer of `JournalEntry`/`JournalLine`
  (UoW with snapshot regen).
- `ChartOfAccountsService` — versioned COA.
- `AccountingPeriodService` — open/close periods.
- `SegregationOfDutiesService` — SoD enforcement (postingUser ≠ approver).
- `AccountingEventEmitterService` — emits outbox events.
- `BeancountSnapshotService` — generates the mmap snapshot.
- `OutboxMerkleRootService` — Phase 1l Merkle root for audit.
- `HttpAccountingSidecarClient` — calls the sidecar.
- `AccountingApprovalGuard` — TIER-2 approval gate.
- `AccountingScopedToolGatewayService` — exposes `nc.accounting.*` tools
  through the chat agent.
- Tools: `NpvTool`, `IrrTool`, `MirrTool`, `AmortizeLoanTool`.

### 6.2 Unit-of-Work
Every ledger write goes through `LedgerRepositoryService` which writes
`JournalEntry` + `JournalLine` + outbox event + triggers snapshot regen
in a single UoW. SoD check + tenant scoping happen before any DB write.

### 6.3 SoD enforcement
Two layers:
1. **DB CHECK constraint:** `posting_user_id <> approved_by_user_id` on
   `JournalEntry` (`20260730_acct_capability_init` migration).
2. **Application guard:** `AccountingApprovalGuard` rejects the action
   before it ever reaches the repo.

### 6.4 Tools (`nc.accounting.*`)
`backend/src/modules/accounting/tools/accounting-tools.providers.ts`:
- `NpvTool` — calls `POST /v1/compute/investment/npv`.
- `IrrTool` — calls `POST /v1/compute/investment/irr`.
- `MirrTool` — calls `POST /v1/compute/investment/mirr`.
- `AmortizeLoanTool` — calls `POST /v1/compute/loan/amortize`.

Each tool:
- Is `READ_ONLY` or `APPROVAL_REQUIRED` depending on context.
- Carries a Zod schema for input validation.
- Includes `tenantId` from `TenantContextService`.
- Records every invocation to the audit log.

### 6.5 Scoped token
`AccountingTokenService.issue({ tenantId, scope, expiresAt })` returns a
JWT-like signed token (HMAC-SHA256 with shared secret). The sidecar
verifies via `infra/_common/scope_token.py`.

### 6.6 What this module is NOT (yet)
- AR/AP/payroll/fixed-asset/bank-recon/tax subledgers (planned).
- The Beancount snapshot generator (Phase 1k — planned).
- Merkle root background job (Phase 1l — planned).
- `nc.accounting.*` tools wired into the chat agent graph (Phase 1j —
  partly done; see `pending-tasks.md`).

## 7. Migration: `20260730_acct_capability_init`

Introduces (verified against `backend/prisma/migrations/20260730_acct_capability_init/*.sql`):

- **`ChartOfAccount`** — chart-of-accounts root (singular). Lines live as
  rows on the chart itself; there is no separate `ChartOfAccountsVersion`
  or `LedgerAccount` table.
- **`AccountingPeriod`** — `OPEN | CLOSING | CLOSED | LOCKED` (enum
  `AccountingPeriodStatus` lives in Postgres but is not exposed as a
  Prisma field — Prisma manages it as a string).
- **`UserAccountingRole`** — per-user SoD role tracking
  (`AccountingRole` enum: `POSTING | REVIEWER | VIEWER | ADMIN`).
- **`JournalEntry`** — header row, carries `postingUserId` + `approvedById`.
- **`AccountingRecord`** — subledger lines attached to a `JournalEntry`
  (debit/credit + amount + account reference; the enum
  `postingType` carries `DEBIT | CREDIT`).
- **`AccountingDataset`** — datasets used by Beancount snapshot regen.
- **`AccountingReport`** — generated reports cached at the row level.
- **`AuditFinding`** — audit findings generated by SoD / Merkle-root
  verifications (enum `AuditFindingSeverity` +
  `AuditFindingStatus`).
- **`OutboxMerkleRoot`** — daily Merkle root per tenant, computed from
  the outbox.

Plus a partial CHECK constraint on `JournalEntry`:
```sql
CHECK ("approvedById" IS NULL OR "approvedById" <> "postingUserId");
```
Prisma cannot express this directly; it is added in raw SQL inside the
migration. Enforces SoD at the DB level (Invariant §4 - Accounting in
`fixes.md`).
