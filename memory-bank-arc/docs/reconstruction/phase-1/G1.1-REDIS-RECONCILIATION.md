# G1.1 — Redis Usage Reconciliation

**Date:** 2026-07-26

## Claim vs. Reality

The previous G1 evidence pack (`G1-MODULE-WIRING.md`) listed `CacheModule (@Global) — Redis` as part of the application infrastructure. This is a contradiction:

- The implementation plan (§2.5) explicitly chose **PostgreSQL-backed outbox** over Redis/BullMQ
- The new AWL modules do not use Redis
- The new `TenantFlagsService` uses an in-memory `Map` cache with 30s TTL

**Conclusion:** The new AWL modules do not depend on Redis.

## What Uses Redis in the Existing Codebase

`CacheModule` and Redis are used by the pre-existing platform for:
- Session caching (legacy auth)
- Rate limiting counters (legacy)
- Agent response caching (legacy)
- General-purpose key-value store (legacy)

These are **out of scope** for the AWL reconstruction.

## What This Means for G1.1

1. The golden path is **PostgreSQL-only** at the data layer
2. The new `OutboxService` is the durable queue
3. The new `TenantFlagsService` has its own in-memory cache (30s TTL) with database fallback
4. The new `IdempotencyService` uses PostgreSQL `IdempotencyRecord` table — no Redis

## What Must Be Documented

The application's existing `app.module.ts` imports `CacheModule` and `RedisService` (legacy). These are NOT imported by any new AWL module. The legacy module is preserved for backward compatibility.

**Operational note:** If Redis is unavailable, only legacy features are affected. The AWL golden path remains fully functional.
